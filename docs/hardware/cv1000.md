# CV1000 hardware notes (for the recompiler and runtime)

Sources: MAME `src/mame/cave/cv1k.cpp` (BSD-3-Clause, David Haywood, Luca Elia, MetalliC), plus our own
disassembly of `futaribl`. Only facts are recorded here; no game code.

## Board variants
| | CV1000-B | CV1000-D |
|---|---|---|
| Work RAM | 8 MB @ `0x0C000000` | 16 MB @ `0x0C000000` |
| U4 program flash | 2 MB (29LV160BB) | 4 MB (S29JL032H) |
| RTC battery | yes | no |
| MAME machine | `cv1k` | `cv1k_d` |
| Games | mushisam, ibara, ibarablk, espgal2, mushitam, pinkswts, futari15/10, **futaribl**, mmpork, deathsml | dsmbl, ddpdfk, dfkbl (+ akatana, ddpsdoj: removed from MAME's game list at rightholder request) |
`mmmbanc` is CV1000-B with a serial touch panel on SCIF2.

## CPU
Hitachi SH7709S (SH-3), **big-endian**, 102.4 MHz (12.8 MHz × 8). No FPU.
U4 is dumped byte-swapped per 16-bit word (`ROM_LOAD16_WORD_SWAP`): swap byte pairs before decoding.

## Physical memory map (CPU uses P1/P2 mirrors: `0x8…`, `0xA…`, `0xB…` uncached)
| Physical | What |
|---|---|
| `0x00000000-0x003FFFFF` | U4 ROM (2 MB, mirrored once on CV1000-B) |
| `0x0C000000-0x0C7FFFFF` | Work RAM (8 MB; 16 MB on -D). Blitter reads its command lists/data from here |
| `0x10000000-07` | NAND (U2): +0 data r/w, +1 command, +2 address (accessed via `0xB0000000`) |
| `0x10400000-07` | YMZ770 sound writes |
| `0x10C00000-07` | RTC9701 serial EEPROM/RTC: +1 bit I/O (bit0 data, bit1 clock, bit2 CS active-low); +3 NAND CE |
| `0x18000000-57` | Blitter registers (`cv1k_v.cpp`); `0x18000050` = DIP switches |
| `0xF0000000-…` | SH-3 cache address array (treat as RAM) |
| SH-3 port J | FPGA config/data (blitter `fpga_r/w`) |

## Inputs (active low)
- Port C: b0 service coin, b1 test (JAMMA), b2 coin1, b3 coin2, b4 start1, b5 start2
- Port D: P1 b0 up, b1 down, b2 left, b3 right, b4-b7 buttons 1-4
- Port L: P2, same layout as port D
- Port E: b5 = NAND ready (1 = ready)
- Port F: b1 = S3 test button

## Video and timing
- 320×240 visible, 407×262 total, pixel clock 6.4 MHz → **60.0183806 Hz**.
- IRQ2 at vsync. End-of-blit should raise IRQ1 (nothing depends on it).
- VRAM and source graphics: RGB555 + 1-bit transparency. Alpha values 8-bit; tint "normal" = 0x20.
- Slowdown is real hardware behavior: NAND reads are byte-at-a-time from uncached space (~10 CPU cycles
  each), plus cache flushes. These shape boss-pattern slowdown (e.g. Futari stage 5). Our timing model
  must charge these costs to reproduce slowdown; the "no slowdown" option simply stops charging them.

## NAND (U2, Samsung K9F1G08U0M)
- 1024 blocks × 64 pages × (2048 data + 64 spare) = 0x8400000 bytes. The dump includes spare bytes.
- Spare bytes are Cave metadata, not standard bad-block markers (page spare ends with ASCII `CV100000`).
  Cave wrote around bad blocks and keeps its own block table. **The runtime serves raw page reads and lets
  the game's code parse them**, so no per-game asset format needs reverse engineering.
- Game checks the NAND ID: allowed 0x98/0x76, 0x98/0x79, 0xEC/0xF1 (K9F1G08U0M).

## Boot sequence (futaribl; expect the same shape on other titles)
1. Reset at `0xA0000000`: SP = `0x0C800000`, SR = `0x700000F0`, **VBR = `0x8C000000`**, GBR = `0xFFFFFF00`
   (on-chip registers), bus/port setup.
2. Copy ROM `0x000000-0x050FFF` → RAM `0x0C000000` (`0x51000` bytes).
3. `jsr 0x0C002AC4(r4=0xAC051000, r5=0xA0051000)`: unpacks ROM data at `0x51000` into RAM `0x0C051000`.
   The block header begins `002C85B8` (likely the unpacked size, 2.9 MB). ROM entropy: 0x70000-0x17FFFF ≈ 7.6
   bits/byte (packed), so the main program lives packed in ROM and only exists in full in RAM.
4. Copy exception stubs to `0xAC000100`, `0xAC000400`, `0xAC000600` (VBR+0x100 general, +0x400 TLB,
   +0x600 interrupts).
5. `jsr 0x0C002A30(0)`, `jsr 0x0C05DBD0`, then `jmp 0x0C062FA0` (main program entry).

**Consequence for the recompiler:** we do not decode the packing format. The setup tool runs the boot code
on our own SH-3 interpreter until it reaches the main entry, then recompiles the RAM image. This works for
every CV1000 title without per-game unpacking code.

## Idle loops (from MAME speedups; useful anchors)
| init | Games | idle RAM var | idle PC |
|---|---|---|---|
| init_mushisam | mushisam, mushisamb | `0x0C0024D8` | `0x0C04A2AA` |
| init_ibara | mushisama, ibara, ibarao | `0x0C0022F0` | `0x0C04A0AA` |
| init_espgal2 | espgal2 (all) | `0x0C002310` | `0x0C05177A` |
| init_mushitam | mushitam (all) | `0x0C0022F0` | `0x0C04A0DA` |
| init_pinkswts | pinkswts, ibarablk, futari15/10, **futaribl**, mmpork, mmmbanc | `0x0C002310` | `0x0C05176A` |
| init_deathsml | deathsml | `0x0C002310` | `0x0C0519A2` |
| init_ddpdfk | ddpdfk, dfkbl, dsmbl | see driver | see driver |
The idle PC is the frame-wait loop: it polls the RAM variable, which the vsync IRQ updates.
